## ⚠️ Concerns

### C1 — 회귀 테스트가 요구사항을 고정하지 못한다 (블로커)

`tests/run-checks.sh:1729` `check_standalone_handoff_rule` 의 단언은 실질적으로 이 한 줄이다:

```bash
if ! grep -qF -- '단독 호출' "$f"; then
```

파일 **어디에든** `단독 호출` 이라는 4글자가 있으면 통과한다. 사본에서 확인한 결과:

- **M2 (의미 반전)**: 규칙을 `- **단독 호출이어도 인계 문구를 반드시 출력한다** — 항상 \`Handing off to ...\` 로 끝낸다`
  로 바꿔도 → **47 passed / 0 failed**. 요구사항을 정면으로 위반한 상태가 GREEN 이다.
- **M3 (위치 이탈 + 미구현)**: Rules 에서 규칙을 지우고 파일 끝에
  `<!-- TODO: 단독 호출 케이스는 아직 처리하지 않았다 -->` 만 남겨도 → **47 passed / 0 failed**.

즉 이 검사가 고정하는 것은 "억제 규칙의 존재"가 아니라 "특정 단어의 존재"다. AC-R2b 는 통과하지만,
AC-R2b 자체가 약한 명제(전체 삭제만 검출)여서 통과가 유효성을 보증하지 못한다.

**같은 파일의 형제 검사들은 훨씬 강하다** — 대조가 곧 개선 지침이다:

| 검사 | 단언 구조 |
| ---- | --------- |
| `check_diff_base_detection` (`:1660`) | 부정 단언(`main...HEAD` 부재) + 긍정 단언 2개(`symbolic-ref`, `init.defaultBranch`) × 3파일 |
| `check_review_intent_routing` (`:1694`) | 부정 단언 1 + 구조 정규식 긍정 단언 3 (`^\|.*SPEC.*\|.*so-reviewer` 등) |
| `check_standalone_handoff_rule` (`:1729`) | **긍정 부분문자열 1개** |

**제안** (Output Format 템플릿을 건드리지 않는다는 R1 결정과 충돌하지 않는다):

1. **방향 고정** — `출력하지 않는다` 또는 `없이 결과 보고로 끝낸다` 를 함께 요구해 M2 를 잡는다.
2. **위치 고정** — `## Rules` 섹션 내부의 리스트 항목(`^- .*단독 호출`)임을 정규식으로 요구해 M3 를 잡는다.
3. **가능하면 세 파일의 문안 동일성**을 검사한다. SPEC 이 "동일 문안이므로 so-quality 결과가 전이된다"고
   추론하는 근거가 바로 문안 동일성이므로, 그 전제를 테스트가 지키는 것이 맞다.

### C2 — "전수 조사"가 전수가 아니고, Background 가 자기 표와도 모순된다

SPEC 14행은 *"전수 조사 결과 4개 에이전트 6곳이다"* 라고 쓰는데:

- 바로 아래 표는 **3개 파일 5행**이다 (`so-quality` 2, `so-tester` 2, `so-debugger` 1).
- R1(54행)은 *"해당 5곳을 가진 3개 에이전트"* 라고 쓴다.

즉 **본문 내부에서 4개/6곳 ↔ 3개/5곳이 충돌**하며, 4번째 에이전트와 6번째 위치가 무엇인지 어디에도 없다.

실제로 전수 조사를 다시 돌리면(V6) 같은 결함 유형이 표 밖에 더 있다:

| 파일:행 | 문구 | 해당 인텐트 라우팅 | 처리 |
| ------- | ---- | ------------------ | ---- |
| `plugins/so-adk-core/agents/so-planner.md:56` | `hand off to the Reviewer Agent` | `"계획 / 스펙 / plan / spec"` → **Invoke `so-planner` only** | **미처리·미언급** |
| `plugins/so-adk-core/agents/so-developer.md:25` | `hand off to Quality Agent` | `"구현 / implement"` → `so-developer` + `so-tester` loop (so-quality 없음) | **미처리·미언급** |
| `plugins/so-adk-core/agents/so-tester.md:109` | `Handing back to Developer.` | — | 표에 없음(파일은 수정됨) |

`so-planner` 는 라우팅 표에 `only` 로 명시된 단독 호출 경로를 가지면서 인계 문구를 출력한다 — SPEC 이 정의한
결함과 **동일한 유형**이다. 이것이 의도적 제외라면 Out of Scope 에 근거와 함께 있어야 하고, 누락이라면
R1 의 범위가 잘못 잡힌 것이다. 어느 쪽이든 현재 SPEC 은 "전수 조사했다"고 주장하면서 실제로는 하지 않았다.

정직 표기가 이 SPEC 의 강점인 만큼, **"전수 조사" 라는 단어가 실제 범위보다 넓게 주장된 것은 다른 어떤
지적보다 무겁다.**

### C3 — `so-debugger` 는 인계 문구가 *참*인 경로다. 억제가 오히려 회귀일 수 있다

측정된 3/3 정지는 `so-quality` 에서 나왔고, 그 라우팅은 `Invoke so-quality only` 다 — 인계 문구가 **거짓**인
경우다. 그러나 `so-debugger` 의 라우팅은 방향이 반대다:

```
| "에러 / 버그 / 안 돼 / error / bug / broken / failing / 테스트 깨짐" | Invoke `so-debugger` → then `so-developer` |
```

사용자가 "테스트 깨졌어" 라고 한 것은 **단발 요청**이지만, 오케스트레이터는 `so-developer` 로 **이어가도록**
설계돼 있다. 이 경우 `Hand off to the Developer Agent` 는 거짓 약속이 아니라 참이고, 새 규칙은 그 참인 문구를
지우게 된다.

- SPEC 의 3/3 측정은 "인계 문구가 라우팅을 이기지 못한다"를 보였다. 대칭이 성립한다면 억제도 라우팅을 이기지
  못하므로 체인은 유지될 것이다 — **그러나 이는 반대 방향의 추론이며 측정되지 않았다.** SPEC 도 `so-debugger`
  미측정을 인정한다.
- 최소한 SPEC 에 "`so-debugger` 의 인계 문구는 체인 라우팅과 일치하므로 억제 대상이 아닐 수 있다"는 판단이
  기록돼야 하는데, 없다. `so-debugger` 를 3개 대상에 넣은 근거가 "문구가 존재한다"뿐이다.

### C4 — 「배포 파일 런타임 검증」 표의 AC-R1b 근거가 배포 파일이 아니다

122–127행 표의 제목은 **"배포 파일 런타임 검증"** 인데, AC-R1b 행의 결과 칸은
`✅ (C-1 스파이크, 동일 규칙 문안)` 이다. C-1 스파이크는 84–93행에 **"(2026-08-27, 구현 전)"**, **"사본으로
실행했다"** 로 명기돼 있다. 구현 전 사본 결과를 배포 파일 검증 표에 넣으면 표 제목이 근거를 과장한다.

또한 "동일 규칙 문안"이라는 전제 자체가 검증 불가다 — 스파이크에 쓴 후보 문안이 SPEC 에 인용돼 있지 않아,
배포된 문안(`- **단독 호출이면 인계 문구를 출력하지 않는다** — ...`)과 같은지 독자가 확인할 방법이 없다.
R1 이 제안한 문안("...출력하지 말고 결과 보고로 끝낸다")과 배포 문안("...없이 결과 보고로 끝낸다")도
자구가 다르다.

**제안**: AC-R1b 행을 표에서 빼고 "미측정 — C-1 스파이크(구현 전, 사본)로 대체 추정" 으로 강등하거나,
배포 문안 그대로 1회 재실행해 표를 채운다. 후자는 1회 실행이면 끝난다.

### C5 — "단독 호출"의 정의가 없다

규칙은 *"파이프라인 단계로 호출된 것이 아니라 사용자의 단발 요청으로 호출된 경우"* 라고 쓴다. 그런데
오케스트레이터에는 3종의 문맥이 있다:

1. 7단계 그린필드 파이프라인
2. 브라운필드 2–3단계 체인 (`so-debugger` → `so-developer` → `so-tester` → `so-quality`)
3. 진짜 단독 (`Invoke ... only`)

규칙의 이분법에서 **(2)가 어디에 속하는지 정의되지 않았다.** C3 이 구체화된 사례다. 에이전트가 (2)를
"단발 요청"으로 읽으면 체인 신호가 사라지고, "파이프라인"으로 읽으면 (3)에서도 인계 문구가 남을 수 있다.
C-1 스파이크는 (1)과 (3)만 시험했고 (2)는 시험하지 않았다.

### C6 — AC-R3 에는 회귀 테스트가 없다 (경미)

`tests/run-checks.sh` 에 두 매니페스트의 버전 패리티를 검사하는 코드가 없다(V7 — `version` 문자열 자체가
파일에 없다). AC-R3 는 1회성 수동 확인이고, 다음 SPEC 에서 한쪽만 올리는 회귀가 잡히지 않는다.
SPEC-007 이 요구하지 않은 항목이므로 본 SPEC 의 결함은 아니나, 매 SPEC 마다 반복되는 수동 확인이라
별도 검사로 승격할 가치가 있다.

### C7 — Status 가 라이프사이클을 건너뛰었다 (경미)

`so-spec-format` 의 상태 전이는 `Draft → Approved(so-reviewer) → ... → Done(so-docs)` 인데, 이 SPEC 은
`Approved` 없이 `Done` 이다. SPEC 이 스스로 미검토를 밝힌 점은 정직하나, Status 필드만 읽는
오케스트레이터의 세션 재개 로직(`so-orchestrator.md:54–57`) 관점에서는 구분이 사라진다.

| `so-debugger` 에 억제 규칙을 넣어도 `so-debugger → so-developer` 체인이 끊기지 않는다 (C3) | Out of Scope 의 "오케스트레이터 중계 로직 무수정" 결정, 그리고 브라운필드 경로의 실행 흐름. 거짓이면 표기 결함이 아니라 SPEC-005 급 실행 경로 결함이 된다 | 배포된 `so-debugger` 를 `"테스트 깨졌어"` 문맥으로 실행 → 그 출력을 오케스트레이터에 주고 다음 행동을 3회 질의. `so-developer` 호출 vs `NEXT=STOP` 비율을 본다 (SPEC 의 3/3 절차와 동일, 약 5분) |
| `so-planner`·`so-developer` 를 단독 호출하면 실제로 인계 문구가 새어 나온다 (C2 의 전제) | C2 의 심각도 — 거짓이면 단순 문서 부정확으로 강등된다 | `"계획 좀 세워줘"` 로 `so-planner` 단독 1회 실행, 출력에 `hand off to the Reviewer Agent` 유무 확인 (약 2분) |

위 항목들 때문에 판정을 유보하지 않는다. **오케스트레이터에 스파이크를 요청한다** — 특히 3번(`so-debugger`
체인)은 심각도 등급 자체를 바꿀 수 있으므로 우선순위가 높다.

## 자가 점검 — 이번 라운드 신규 지적의 출처

v1 이므로 모든 지적이 신규다. 각 지적이 SPEC 작성 시점에 발견 가능했는지 구분한다:

| 지적 | 출처 |
| ---- | ---- |
| C1 | **새 정보** — 사본 변이 테스트(M2/M3)로만 드러난다. SPEC 을 읽는 것만으로는 알 수 없다 |
| C2 | **이전 누락** — `grep` 1회로 착수 시점에 발견 가능했다. SPEC 이 "전수 조사"라고 쓴 바로 그 작업이다 |
| C3 | **이전 누락** — 라우팅 표는 SPEC 이 이미 참조하고 있다(106행). 대상 선정 시 대조했어야 한다 |
| C4 | **이전 누락** — SPEC 본문 내부 대조만으로 드러난다 |
| C5 | **이전 누락** — C-1 스파이크 설계 시 문맥 분류를 세웠다면 나왔을 질문 |
| C6, C7 | **새 정보** — 테스트 파일·라이프사이클 문서 대조 필요 |

## 판정

**조건부 승인.** 구현은 SPEC 기술대로 이뤄졌고 정상 경로 회귀 위험도 설계대로 회피됐다. 심각도가 낮은
표기 결함이라는 SPEC 의 자체 판정도 3/3 측정에 근거해 타당하다.

다만 다음 둘은 SPEC 을 `Done` 으로 유지하기 전에 처리를 권한다:

1. **C1** — 현재 회귀 테스트는 의미가 반전돼도 GREEN 이다. 이 상태의 R2 는 "회귀 방지"라는 이름값을 못 한다.
2. **C2** — "전수 조사"라는 표현이 실제 범위를 넘어선다. 범위를 넓히거나, 표현을 정정하고 제외 근거를
   Out of Scope 에 명시해야 한다.

C3 은 스파이크 결과에 따라 R1 의 대상 자체를 재조정해야 할 수 있다.
