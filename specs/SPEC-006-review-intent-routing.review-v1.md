## ⚠️ Concerns

### C1 (High) — 회귀 테스트가 **이 SPEC 의 핵심 결함 F1** 을 고정하지 못한다

`check_review_intent_routing` 의 코드 리뷰 위임 검사는 다음이다 (`tests/run-checks.sh:1717`):

```bash
grep -E '^\|.*(코드 리뷰|code review).*\|.*code-review' "$f"
```

`.*code-review` 는 부분 일치이므로 **`so-adk-core:code-review` 도 통과한다.** M5 에서 위임 대상을 환각 스킬명으로 되돌렸는데 검사는 `PASS` 했다.

F1 은 이 SPEC 이 "확정된 결함 세 가지" 중 유일하게 **실질 피해(호출 실패)** 가 있다고 판정한 항목이고, 정정된 심각도 절이 "중간" 판정의 근거로 삼은 것도 F1 이다. 그 F1 만 회귀 그물을 빠져나간다. 라우팅 표의 바로 이웃 행이 `` `so-adk-core:pr` skill `` 로 네임스페이스 표기를 쓰므로 **유추에 의한 재오염 경로가 실재한다** — F1 의 환각도 정확히 그 형태였다.

제안(둘 다):

```bash
# 위임 대상은 네임스페이스 없는 내장 스킬이어야 한다 (F1 회귀 방지)
if grep -qF -- 'so-adk-core:code-review' "$f"; then
  echo "[FAIL] $name: nonexistent plugin skill 'so-adk-core:code-review' referenced (F1)" >&2
  failed=1
fi
```

그리고 표 행 자체에 **"내장"** 을 명기한다 — 현재 행 문언 `` `code-review` 스킬로 위임 `` 에는 내장이라는 단서가 없고, 그 정보는 표에서 19줄 떨어진 프로즈 절에만 있다.

### C2 (High) — R3/AC-R3(대상 불명 되묻기)를 고정하는 검사가 **아예 없다**

M3 에서 `"리뷰해줘" (대상 불명)` 행을 통째로 삭제했는데 전체 스위트가 그대로 통과했다. 원인은 R5 요구사항 목록 자체가 검사 3종만 열거하고 R3 를 빠뜨린 것이며, `run-checks.sh` 머리말 매핑도 이를 그대로 반영한다 (`SPEC-006 AC-R1/R2/R4/R5` — R3 없음).

결과적으로 **AC-R3 는 `[x]` 로 체크되어 있으나 그 근거는 런타임 n=1 측정 1회뿐**이고, 해당 행이 향후 편집에서 사라져도 아무도 모른다. F2(대상 불명 발화 오배송)는 두 측정 도구 모두에서 재현된 확정 결함이었으므로, 그 처방만 무방비인 것은 균형이 맞지 않는다.

제안:

```bash
# AC-R3 — 대상 불명 발화는 되묻기로 라우팅된다
if ! grep -E '^\|.*리뷰해줘.*\|.*(되묻|물어|ask)' "$f" &>/dev/null; then
  echo "[FAIL] $name: no clarify-first row for ambiguous review request" >&2
  failed=1
fi
```

> 계열 지적: SPEC-005 review-v1 의 C2("R5 회귀 테스트가 R2·R3 를 전혀 고정하지 않는다")와 **같은 실패 패턴이 연속 두 SPEC 에서 반복됐다.** 회귀 검사를 작성한 뒤 "각 R 을 하나씩 되돌려 FAIL 하는지" 확인하는 절차를 R5 류 요구사항의 표준 항목으로 승격할 것을 권한다.

### C3 (Medium) — 정직 표기의 "측정 불가" 사유가 **사실이 아니다** (B-1 은 측정 가능했고, 양성이다)

SPEC 은 두 곳에서 이렇게 적었다.

> 실제로 `code-review` 스킬이 호출·실행되는지는 확인하지 않았다 — 헤드리스 세션에 플러그인이 로드되지 않아 측정 불가였다(B-1 잔여).

이 사유는 성립하지 않는다.

- `claude --help` 기준 `--plugin-dir` 는 `-p`(헤드리스)에서도 유효한 플래그다.
- **SPEC-005 가 이미 `pr` 플러그인 스킬의 런타임 검증을 마쳤다**(v1.2, 픽스처 I·J). 같은 저장소의 직전 SPEC 이 반증 사례다.

본 검토에서 직접 실측했다. 픽스처(`return x/0` → `return eval(x)`, 미커밋 1건)에서 `"코드 리뷰해줘"` 를 헤드리스로 넣은 결과 관측된 tool_use 순서는 다음과 같다.

| 순서 | tool_use | 입력 |
| ---- | -------- | ---- |
| 1 | `Skill` | `{'skill': 'code-review'}` |
| 2 | `Bash` | `git status` / `git diff @{upstream}...HEAD` / `git diff HEAD` |
| 3 | `Read` | `a.py` |
| 4 | `Bash` | 주변 사용처 탐색 |
| — | 결과 | `a.py:2` 의 `eval()` 임의 코드 실행 지적(CWE-95) 보고, 워킹트리 무변경 |

즉 **라우팅 선택에서 끝나지 않고 내장 `code-review` 스킬이 실제로 호출·실행되어 findings 를 반환했다.** 부수적으로 SPEC-005 의 기준선 감지(`@{upstream}` → `git diff HEAD` 폴백)가 실사용 경로에서 작동하는 것도 함께 관측됐다.

조치: B-1 을 **"측정 완료 — 양성"** 으로 승격하고, 정직 표기 두 곳의 사유 문구를 정정할 것. 남는 한계는 "측정 불가"가 아니라 **n=1, sonnet, 픽스처 1종, 그리고 plan mode 1회 + 실행 1회** 다.

### C4 (Low) — 사용자 노출 도움말에 코드 리뷰 진입점이 없다

`so-orchestrator.md:419-424` 의 help 가이드는 `"이 코드 리팩토링해줘 → Quality Agent"`, `"보안 검토해줘 → Security Agent"` 는 안내하지만 **코드 리뷰는 한 줄도 없다.** F3 의 원인이 "표에 행이 없어 모델이 즉흥 대응"이었다면, 사용자 쪽에도 같은 공백이 남아 있는 셈이다. `"코드 리뷰해줘"      → 내장 code-review 스킬` 한 줄 추가를 권한다(문서 변경, 회귀 위험 없음).

### C5 (Low) — 내장 스킬 부재 시 폴백이 미정의다

R2 는 "동명의 로컬 스킬이 있으면 그쪽이 우선"만 다루고, **스킬이 아예 없는 환경**(구버전 Claude Code, `--disable-slash-commands`, 스킬 비활성)의 동작을 정의하지 않는다. 이 경우 오케스트레이터는 다시 즉흥 대응으로 되돌아가며, 그것이 바로 F3 다. 최소한 프로즈 절에 "내장 스킬을 찾을 수 없으면 `so-preflight` 로 폴백하지 말고 사용자에게 부재를 알린다" 한 문장을 권한다.

### C6 (Low) — 정직 표기 마지막 줄이 이 리뷰로 stale 이 된다

> **`so-reviewer` 검토를 거치지 않았다** — `review-v*.md` 가 없다.

본 파일 생성으로 무효가 된다. 검토 이력에 v1.2 행(사후 검토 수행, C1·C2 보강)을 추가하고 해당 줄을 갱신할 것.

### C7 (Low, 정보) — 구현 결과의 테스트 수치가 시점 수치다

"45 → **46 passed**" 는 SPEC-007 의 `check_standalone_handoff_rule` 추가 이전 값이며 현재는 47 이다. 오류는 아니나 `(SPEC-006 시점)` 을 병기하면 이후 대조가 쉬워진다.
