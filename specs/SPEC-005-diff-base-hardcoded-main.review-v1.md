## ⚠️ Concerns

### C1 (High) — 1단계-2 `@{u}` 가 feature 브랜치에서 트렁크를 **자기 자신**으로 오탐한다

`git rev-parse --abbrev-ref @{u}` 는 트렁크가 아니라 **현재 브랜치의 upstream** 을 반환한다.
`refs/remotes/origin/HEAD` 가 없는 저장소에서 feature 브랜치를 push 해 두면 이 값은
`origin/feature/x` 이고, `origin/` 을 떼면 트렁크 = `feature/x` = 현재 브랜치가 된다.
그러면 2단계 (a)의 “현재 브랜치가 트렁크와 **다르면**” 조건이 거짓이 되어 **트렁크 비교가 통째로
건너뛰어진다.**

실측(스크래치패드 픽스처, 커밋 3개짜리 push 된 feature 브랜치):

```
트렁크 탐지 결과 = feature/x  / 현재 = feature/x
(a) 건너뜀   (b)=0 files   (c)=0 files   (d)=rce.py
정답 범위 main...HEAD = rce.py secret.py sql.py
```

채택된 범위는 (d) `HEAD~1` 로 **1파일**, 정답은 **3파일**이다. 누락된
`secret.py`(하드코딩 시크릿)·`sql.py`(SQL 인젝션)는 정확히 `so-security`·`so-preflight` 가
잡아야 할 대상이다. 결과는 오류가 아니라 **부분 리뷰 후 조용한 통과** — SPEC 22행·79행이
없애려던 “안전 게이트의 침묵”과 **동일한 실패 모드**다.

- 발생 조건: `origin/HEAD` 미설정(실측 16개 중 1개, 6%) **+** feature 브랜치 **+** upstream 설정.
- 픽스처 E(`origin/HEAD` 없음 + upstream 있음)는 이 조합을 덮지 못한다 — 결과가 `origin/main`
  이었으므로 트렁크 브랜치 위 구성이었던 것으로 보인다(SPEC에 브랜치 위치 미명시, Q1 참조).
  즉 실측 표의 `sogul` 이 “유효한 보완재”로 판정된 것은 **트렁크 위에 있었기 때문**이며, 이
  조건이 빠지면 보완재가 아니라 오답원이 된다.
- `pr` 스킬은 더 나쁘다 — (b) 미커밋 제외 설계 때문에 (a) 건너뜀 → `@{u}...HEAD` 공집합 →
  `HEAD~1` 로 떨어져 **PR 본문이 마지막 커밋 하나만 요약**한다.
- 제안 수정(3행): 1단계-2에서 얻은 이름이 **현재 브랜치와 같으면 트렁크로 채택하지 않고 1단계-3
  (`main`→`master`→`develop` 실재 확인)으로 내려간다.** 기존 픽스처 B·E 를 깨지 않는다.

### C2 (High) — R5 회귀 테스트가 R2·R3 를 전혀 고정하지 않는다

`check_diff_base_detection` 이 보는 것은 세 파일당 3가지뿐이다: `main...HEAD` 부재,
`symbolic-ref` 존재, `init.defaultBranch` 존재. 즉 **R1 만 고정한다.**

사본에서 다음 3가지를 삭제하고 재실행했다:

1. “넷 다 비면 … **판정을 유보한다** (GO 를 내지 않는다)” (R2)
2. “### 3단계 — 기준선 명시” 절 전체 (R3)
3. Rules 의 “**변경이 없으면 GO 가 아니다**” 행

결과: **`[PASS] check_diff_base_detection`.**

D2 가 88% 로 지배적인 결함이고, 그 D2 를 막는 유일한 안전장치가 `판정 유보` 규칙인데
**그 방어선만 회귀 보호가 없다.** SPEC 은 A-3 를 “미측정”으로 정직하게 표기했으나, 본 리뷰의
측정 결과 A-3 는 **음성**이다 — 완화책(“탐지 문구 존재 검사를 함께 걸어 완화”)이 실제로 완화하는
범위는 R1 에 한정된다. 167행의 A-3 상태와 139행의 R5 문구는 이 측정 결과를 반영해 갱신돼야 한다.

- 제안: `판정을 유보`(또는 `판정 유보`)·`기준선:` 문자열 존재 검사 2줄 추가. 비용 대비 효과가
  현행 3검사와 동급이다.

### C3 (Medium) — `pr/SKILL.md` 의 `git log <기준선> --oneline` 이 기준선 (c)에서 전체 이력을 낸다

`pr/SKILL.md:9` 는 “그 기준선으로 `git diff <기준선>` 과 `git log <기준선> --oneline` 을 실행”이라고
지시한다. `git diff` 는 세 후보 모두에서 의도대로 동작하지만 `git log` 는 그렇지 않다.

이 저장소에서 실측:

```
git log HEAD~1 --oneline      → 50 commits   (전체 이력)
git log HEAD~1..HEAD --oneline →  1 commit    (의도한 것)
```

기준선 (c) `HEAD~1` 이 채택되면 PR 본문 초안이 저장소 전체 이력 50건을 근거로 작성된다.
(a) `<트렁크>...HEAD` 도 `git log` 에서는 symmetric difference라 트렁크 전용 커밋까지 포함한다
(구 코드 `git log main...HEAD` 부터 있던 문제이며 이번 수정으로 해소되지 않았다).

- 제안: `git log` 는 `<기준선의 시작점>..HEAD` 형태를 쓰도록 1단계 문구를 분리한다.
- 픽스처 I(feature 브랜치)·J(커밋 없음)는 (c) 경로를 밟지 않아 이 결함을 노출하지 않았다.

### C4 (Medium) — (b) `git diff HEAD` 는 untracked 파일을 보지 못한다

2단계 (b)는 “미커밋 변경”을 의도하지만 `git diff HEAD` 는 **추적되지 않는 새 파일을 포함하지
않는다.** 새 파일만 추가된 상태는 공집합으로 판정되어 (c)/(d)로 내려가고, 그 새 파일은 어느
범위에도 들어가지 않는다.

이 저장소가 지금 그 상태다:

```
$ git status --porcelain | grep '^??'
?? specs/SPEC-007-standalone-handoff-leak.md
$ git diff HEAD --name-only | grep -c 'SPEC-007'
0
```

보안 게이트 관점에서 방향이 나쁘다 — 새로 추가된 파일(설정·키·스크립트)이 시크릿을 담을 확률이
기존 파일 수정보다 높은데, 그쪽이 우선적으로 누락된다.

- 제안: (b)를 `git status --porcelain` 기준으로 판정하고, 범위에 untracked 파일 목록을 함께 넘긴다
  (또는 `git add -N` 없이 `git diff HEAD` + untracked 파일 직접 Read).
- 픽스처 F·L 이 이 경계를 덮었는지 SPEC 기재만으로는 알 수 없다(Q2 참조).

### C5 (Low) — 우선순위 체인이 합집합이 아니라 “첫 비어 있지 않은 것”이다

feature 브랜치에서 (a)가 비어 있지 않으면 미커밋 변경은 리뷰되지 않는다. `so-preflight` 는
“머지 준비 완료”를 판정하는 게이트인데, 커밋되지 않은 변경이 남아 있다는 사실 자체가 판정에
영향을 주지 않는다. 설계상 의도된 단순화일 수 있으나 SPEC 어디에도 이 트레이드오프가 적히지 않았다.

- 최소 조치: (a) 채택 시에도 미커밋 변경이 존재하면 출력에 한 줄 경고. 기준선 체인은 그대로 둔다.

### C6 (Low) — R4 문구와 구현이 어긋난다

R4 는 “세 파일 전부에 **동일 규칙**을 적용한다”이지만, 구현 결과 250행은 `pr` 이 “에이전트 2종과
**의도적으로 다른** 3단 체인”이라고 적는다. 구현 판단은 옳으나(C3 항의 근거와 별개로 PR 대상은
커밋된 변경이 맞다) **R4 가 갱신되지 않아 SPEC 내부에 모순이 남았다.** 요구사항을 읽고 구현을
검증하는 다음 사람이 불일치를 결함으로 오독한다.

- 제안: R4 를 “세 파일에 동일한 **1단계**를 적용한다. 2단계는 `pr` 만 미커밋을 제외한 3단이다”로 정정.

### C7 (Low) — `so-security` 에 `so-preflight` 의 유보 장치가 대응되지 않았다

`so-preflight` 는 R2 를 위해 (1) 판정 상태 `⏸️ 판정 유보` 신설, (2) Rules 에 “변경이 없으면 GO 가
아니다” 추가 — 두 겹으로 고정했다. `so-security` 는 복사된 블록의 “판정을 유보한다 (**GO** 를 내지
않는다)” 한 줄뿐이고, 그 문장의 “GO” 는 `so-security` 의 판정 어휘(BLOCK / CONDITIONAL / PASS)에
존재하지 않는다. Output Format 에도 유보 상태가 없다. 기존 Rules 163행(“diff 가 비면
‘변경된 파일이 없습니다’ 보고 후 종료”)이 실질적으로 같은 일을 하므로 현재 동작은 무해하나,
**인라인 3벌 복제 시 대상별 어휘 조정이 누락된 사례**다.

- 제안: `so-security` 블록의 해당 문장을 “판정(PASS 포함)을 내지 않는다”로 조정.

### C8 (Low) — 정직 표기 313행이 본 리뷰로 stale 이 된다

“**본 SPEC 은 `so-reviewer` 검토를 거치지 않았다.** SPEC-001·004 와 달리 `review-v*.md` 가 없다.”
— 본 파일 생성 시점부터 거짓이다. 갱신 필요.

  분리할 것인가? `HEAD~1` 경로는 이번 수정으로 **새로 생긴** 경로이므로 전자를 권한다.
- **Q4** — C1·C2 를 SPEC-005 재개(v1.4 + 추가 커밋)로 처리할 것인가, 후속 SPEC-008 로 분리할
  것인가? SPEC-005 는 이미 `Done` 이고 1.0.2 로 배포됐으므로 후자를 권한다.

## 자가 점검 — 이번 라운드 신규 지적의 근거

v1 이므로 전부 신규다. 다만 “왜 구현 중에는 안 잡혔는가”를 항목별로 밝힌다.

| 지적 | 미포착 사유 |
| ---- | ----------- |
| C1 | 픽스처 설계가 **트렁크 위 구성(D2)** 에 집중돼 feature 브랜치 + `origin/HEAD` 부재 조합이 없었다. D2 가 88% 라는 측정이 오히려 D1 측 경계 픽스처를 얇게 만들었다 |
| C2 | A-3 를 “미측정”으로 정직 표기했으나 실제로 **측정하지 않았다.** 측정 비용은 5분이었다 |
| C3 | 런타임 검증이 `git diff` 채택 여부에 집중했고 `git log` 출력을 확인하지 않았다. 픽스처 I·J 가 (c) 경로를 밟지 않았다 |
| C4 | `git diff HEAD` 의 untracked 미포함은 git 의 알려진 동작이나 SPEC 어디에도 검토 흔적이 없다 |
| C5–C8 | 문서 일관성 항목 — 정적 검사·런타임 검증 어느 쪽의 대상도 아니다 |

## 판정

**구현 자체는 되돌릴 필요가 없다.** D1·D2 진단, 요구사항 도출, 3파일 일괄 적용, 런타임 검증
범위는 모두 타당하고 재현됐다. AC 11건 중 재현 가능한 5건(R4·R5a·R5b·R6 및 R4 일괄 적용)은
전부 실측으로 확인했다.

다만 **C1·C2 는 SPEC-005 가 없애려던 실패 모드(안전 게이트의 침묵)를 남은 경로에서 재현한다.**
후속 SPEC 으로 처리할 것을 권고한다. Status 는 `Done` 을 유지한다 — 사후 검토이므로
`Approved` 로 되돌리지 않는다.
