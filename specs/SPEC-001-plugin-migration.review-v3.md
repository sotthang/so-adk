### 2. C-2 대응(R11 재설계)의 성립성 — 단독 심사

#### 2-1. `--plugin-dir`가 정말 공백기를 없애는가

**구조상 성립한다. 단, 이 메커니즘 자체는 F1~F14 어디에도 실측 기록이 없다.**

- 커밋 계획상 `git mv`(커밋 1)부터 레거시 제거(최종 커밋)까지 저장소의 `.claude/agents/`는 부재하다. 즉 **브랜치 전 구간에서 `--plugin-dir`가 유일한 동작 경로**다 — 보조 수단이 아니라 하중을 받는 기둥이다.
- 그런데 F 표에 `--plugin-dir` 항목이 없다. AC-R2c·AC-R3e가 이 플래그를 **사용**하지만, 플래그가 동작한다는 것 자체는 전제로만 놓여 있다.
- 이것은 **F12가 방금 반증한 것과 같은 종류의 미검증 전제**다. 같은 실수 패턴을 한 칸 옆에서 반복할 위험이 있다.

**그럼에도 Draft로 되돌리지 않는 이유**:

1. `--plugin-dir`의 의미론(세션 한정 디렉터리 로드)은 F12가 반증한 "설정 파일 전파" 의미론보다 훨씬 단순하고 상태 의존이 없다.
2. **실패해도 이미 증명된 대체 경로가 있다.** F12의 **대조군이 양성**이었다 — `claude plugin install <name>@<mkt> --scope local/project`는 로컬 디렉터리 마켓플레이스에서 동작함이 실측됐다. 최악의 경우에도 "브랜치에서 1회 로컬 설치"로 즉시 우회된다.
3. 실패의 폭발 반경이 **feature 브랜치 개발 편의**에 한정된다. main도, 기존 curl 사용자도, 저장소 이력도 손상되지 않는다(R11-b, AC-R11c).

→ **I-1**: `git mv` 커밋 **이전**에 `--plugin-dir` 로드를 사전 확인하고, R11-c에 "실패 시 `--scope local` 1회 설치로 폴백(F12 대조군 양성)" 한 줄을 명기할 것.

#### 2-2. 기여자 온보딩이 문서화 이상인가

**아니다 — 문서화가 전부이며, SPEC은 그 사실을 숨기지 않는다.**

- R8(8)·R9·R11-d는 모두 "README에 기재한다"까지다. AC-R8(8)은 **문서에 문장이 있는지**만 검증한다.
- 설치하지 않은 기여자를 탐지할 기계적 수단은 없다. 플러그인이 비활성이면 플러그인 안의 어떤 검사도 실행되지 않으므로 **원리적으로 자기 탐지가 불가능**하다. SPEC의 결함이 아니라 플랫폼의 성질이다.
- **다만 SPEC이 놓친 실질적 방어 1개가 있다**: F13이 "잘못된 설정은 에러 없이 조용히 disabled"를 확정했는데, 온보딩 절차 어디에도 **설치 후 상태 확인 단계가 없다**. AC-R4d는 *커밋된* 스키마를 정적으로 막을 뿐, 기여자 머신에서 조용히 disabled가 된 상태는 잡지 못한다.

→ **I-2**: R8 온보딩 절차에 `claude plugin list`로 두 플러그인이 `✔ enabled`인지 확인하는 단계 추가.

#### 2-3. 🔴 R9/R11의 `--plugin-dir` 위상 오설정 (신규 지적)

**C-2 대응에서 가장 실질적인 결함이다.**

R9와 R11-c는 `--plugin-dir`를 **"전환 작업 중"의 한시적 수단**으로, 명시적 설치를 **"전환 완료 후"의 정상 상태**로 규정한다. 그런데 AC-R4b/F14에 따라 커밋되는 마켓플레이스 source는 **github 형태**다. 결과:

> 전환 완료 후 기여자가 `claude plugin install so-adk-core@so-adk --scope project`를 실행하면, 플러그인은 **GitHub 기본 브랜치에서 받아온 사본**으로 로드된다. 작업 트리의 `plugins/` 편집분은 **세션에 반영되지 않는다.**

즉 이 저장소에서 에이전트/스킬을 수정하는 기여자는 **자기 변경을 테스트하지 못한 채 published 사본을 돌리게 된다** — 에러가 아니라 조용히 그렇게 된다(F13류 무증상 실패의 변종).

- SPEC은 재료를 이미 갖고 있다: R8(3) "플러그인 **자체 개발 중에는** `--plugin-dir`로 세션 한정 로드".
- 그러나 R9/R11-c의 "전환 중"이라는 시간 한정 프레이밍과 **상충**한다. 자체 플러그인을 호스팅하는 저장소에서 `--plugin-dir`는 한시적 우회가 아니라 **상시 개발 모드**다.

→ **I-3**: R9의 2단 구조를 시간축이 아니라 **역할축**으로 고쳐 쓸 것.
- `--plugin-dir` = `plugins/` 하위를 편집하는 개발 세션의 **상시 기본 모드**(전환 중·후 무관)
- `claude plugin install --scope project` = 저장소를 **소비**만 하는 기여자 및 일반 사용자용

### 3. v3에서 새로 유입된 결함 (모순·중복)

#### 🔴 M-1 — AC-R5a 패턴 (1)이 현 저장소에서 **충족 불가능**하다 (실측 확인)

패턴 (2)는 정확하다(§1). **패턴 (1)을 실물에 돌려보면 결과가 다르다.**

```
grep -rE '(^|[^:a-z])/(dev|plan|pr|refactor)([^a-z:]|$)'
```

이 정규식은 `/dev/null`을 **매치한다**(선행 `>` 또는 공백이 `[^:a-z]`, 후행 `/`가 `[^a-z:]`). `plugins/`로 이동할 파일들의 실제 히트:

| 파일 (이동 후 경로) | 행 | 내용 |
| --- | --- | --- |
| `hooks/session-start-resume.sh` | 11, 32 | `cat > /dev/null`, `&>/dev/null` |
| `hooks/post-edit-check.sh` | 12, 36, 37, 42, 47 | `/dev/null` ×5 |
| `agents/so-auditor.md` | 47 | `2>/dev/null` |
| `agents/so-docs.md` | 39 | `2>/dev/null` |

**총 9건.** 어느 것도 스킬 호출명이 아니다.

단순 오타가 아닌 이유:

- AC-R5a를 그대로 구현하면 **영구 FAIL**하고, 연쇄적으로 **AC-R7a("전체 PASS, FAIL 0")도 영구 미달**이 된다.
- 문언대로 "0건"을 맞추려면 **훅 스크립트 내부와 에이전트 본문을 고쳐야** 하는데, 이는 Out of Scope("훅 스크립트 내부 로직 변경 금지")와 R1("에이전트 15개 본문 완전 무수정")을 **정면 위반**한다.
- 구현자는 "AC를 못 맞추거나 / 불변식을 깨거나 / 검사를 몰래 약화시키거나" 셋 중 하나를 강요당한다.

v3는 패턴 (2)에 **"이관 전 실물에 적용하면 4건이 검출되어야 한다"는 자가 검증을 붙였는데(C-4 대응, 매우 좋은 관행), 패턴 (1)에는 같은 자가 검증을 적용하지 않았다.** 붙였다면 9건의 오탐이 즉시 드러났을 것이다.

→ **M-1 (필수)**: 패턴 (1)에 `/dev/null` 제외 명시(예: 후행 `/` 배제 `([^a-z:/]|$)` 또는 `grep -v '/dev/null'`) + **패턴 (2)와 동일한 "이관 전 실물 기대 검출 건수" 자가 검증 조건**을 문언에 못 박을 것(M-2 반영 후 기대치는 `so-quality.md:3` 1건).

#### 🔴 M-2 — R1 "에이전트 본문 완전 무수정" ↔ R5 "구 호출명 전량 갱신" 정면 충돌 (실측 확인)

`.claude/agents/so-quality.md:3` (frontmatter description):

```
description: Code quality enforcer. ... Also invoked by /refactor command.
```

- **R5**는 `plugins/` 하위 모든 구 호출명 참조 갱신을 요구한다 → 이 줄은 `/so-adk-core:refactor`로 **고쳐야 한다**. AC-R5a 패턴 (1)도 이 줄을 정당하게 검출한다(오탐 아님).
- **R1**은 "F4·F11에 따라 **에이전트 15개 파일은 본문 완전 무수정**"이라 단정한다 → **고치면 안 된다**.

같은 한 줄에 대해 두 요구사항이 반대를 지시한다. 어느 쪽을 따르든 다른 쪽 AC가 깨진다.

**해소 방향은 일의적이다 — R5가 옳다.** F4(skills 필드 플레인 해석)와 F11(에이전트 이름 플레인 디스패치)이 확정한 것은 *skills 필드*와 *에이전트 이름 참조*의 무수정 가능성이지, **슬래시 명령 문자열의 무수정**이 아니다. R1의 해당 문장은 F4/F11이 지지하지 않는 범위까지 넘겨짚은 **과잉 일반화**다.

→ **M-2 (필수)**: R1을 "에이전트 15개는 **R5의 구 호출명 치환을 제외하고** 본문 무수정(현 실물 기준 `so-quality.md` 1개 파일, 1행)"으로 카브아웃. AC-R1a(이동 커밋 100% rename)는 **영향 없음** — 이 치환은 커밋 3 소관이므로 C-5의 커밋 경계로 이미 분리되어 있다.

#### 🟡 M-3 — `.gitignore` 해제가 기존 기여자 작업 트리와 충돌 (누락)

R4는 추적 파일 승격에 따른 **장래의 위험 키 유입**(AC-R4c)은 방어했으나 **전환 순간의 충돌**은 다루지 않는다. 이미 로컬에 개인 `.claude/settings.json`을 둔 기여자가 병합분을 pull하면 git이 *untracked working tree file would be overwritten*으로 **체크아웃을 거부**하거나, 기여자가 자기 파일을 커밋해 AC-R4c 위반분이 유입된다. R6 래퍼는 **사용자 프로젝트**만 다루고 이 저장소 기여자는 다루지 않는다.

→ **I-4**: R8 개발 섹션에 1줄 — "기존 로컬 `.claude/settings.json` 보유자는 pull 전 백업 후 삭제하고 개인 설정은 `.claude/settings.local.json`으로 이전."

#### 🟡 M-4 — 커밋된 github source는 병합 이전에는 해석 불가 (문언 보강)

`extraKnownMarketplaces`가 github source이므로 **기본 브랜치**를 가리킨다. 커밋 2에서 파일이 브랜치에 들어와도 병합 전까지 main에는 `.claude-plugin/marketplace.json`이 없어 엔트리는 무의미하거나 조용히 실패한다. 실피해는 없으나(F12로 애초에 기대할 게 없음), R4/R9가 "등록·기록용"이라 부르면서 **"등록조차 병합 이후 유효"**라는 시점 조건을 빠뜨렸다. F13의 조용한 실패와 겹치면 디버깅 시간을 잡아먹는다.

### 4. AC 심사 — 과다한가?

**전제 정정: AC는 59건이 아니라 37건이다.** (R1:2, R2:4, R3:5, R4:4, R5:2, R6:8, R7:4, R8:1, R9:1, R10:1, R11:3, R12:2 = 37. AC-R8 하위 8항목을 개별로 세면 44.)

요구사항 12개 · 파괴적 스크립트 재작성 · 저장소 자기 이관을 포함하는 범위에서 **37건은 과다하지 않다.** 특히 R6이 8건을 쓰는 것은 정당하다 — 사용자 파일을 만지는 유일한 구간이고 실패 모드(jq 부재/비유효 JSON/고아 훅/사용자 수정본)가 실제로 서로 다르다.

#### 4-1. 같은 것을 두 번 재는 AC

| 항목 | 문제 | 권고 |
| --- | --- | --- |
| **AC-R4b ∩ AC-R4d** | 둘 다 github source 형태를 검증한다. R4b가 이미 `.source.source`/`.source.repo`를 요구하므로 R4d는 부분집합 | R4b는 **커밋 여부 + enabledPlugins 키 형식**으로 좁히고 source 스키마 검증은 R4d 단독으로 |

#### 4-2. 기계 검증 불가한데 검증 가능한 척하는 AC

| 항목 | 판정 |
| --- | --- |
| **AC-R11b** | 🟡 **과대 표기.** trailer + `git log --grep`이 기계 검증하는 것은 **"구현자가 스모크를 했다고 선언한 커밋이 최종 커밋 직전에 존재한다"**는 사실뿐이며, 스모크의 **통과**는 증명하지 않는다(자기 신고). v2 대비 **순서 증명력 개선은 사실**이므로 AC는 유지하되, R11-e의 "**기계 검증 가능화**" 표현을 "**선후 관계의 기계 검증 + 스모크 결과의 자기 신고**"로 하향할 것 |

#### 4-3. 구현을 과도하게 규정하는 AC

| 항목 | 문제 | 권고 |
